# 广告完成后连续解锁提示延迟

## 当前优化：连续提示期间暂停准备播放器

- 当前集通过服务端验权、页面在前台且显示连续广告提示时，提前创建或切换同一个官方播放器，使用 `autoplay: false`。不在原生广告中启动新的准备，不允许未授权资源进入播放器。
- 已启动的暂停准备任务在关闭提示、继续广告及临时后台期间保持，避免因为展示状态变化重复初始化。关闭后复用同一实例；准备还未完成时，收尾根据最新前台与遮罩状态决定是否播放。
- 显式 play 早于官方内核 READY 时保留一次意图，READY/COMPLETE 只消费一次；pause、切源和 destroy 清除未执行意图。播放拒绝记录脱敏错误并进入既有自动播放受阻提示。
- 关闭、继续广告、离页、后台及准备完成交错的组件测试通过；普通切集自动播放不变。官方能力依据 `docs/official-player-api-review-2026-09-20.md` 及 BytePlus 初始化参数中的 autoplay 配置。
- 这将初始化等待前移，不保证暂停状态已解码首帧，也不保证零等待；实际首帧收益待新版真机验收。未打包、推送或部署。

## 关闭提示后的重复等待

后续集领取会广播同剧权益变化，原监听无条件重新查询当前集并设置 loading。即使当前集在上一条广告后已经验权和预热，取消连续提示仍可能被这次新请求阻塞。

本次仅在同一连续广告流程、当前路由已验权就绪、收到其他集的逐集奖励时保留当前播放结果；相邻授权仍失效，选集目录后台更新。首次解锁、当前集奖励、切集、VIP 到期仍保留原验权。后台目录更新失败有脱敏诊断且不阻止当前起播。

新增用例让后续重复验权永久等待，修复前出现多余请求，修复后关闭提示仍可挂载当前集；覆盖目录刷新成功与失败。当时聚焦播放器测试 56 项通过，尚未修改官方内核初始化时机；后续暂停准备方案见本文顶部，真机首帧仍需复测。

## 当前方案：服务端结算响应决定下一步

用户确认采用服务端决策。此前并行和批量扫描已从 Mini 连续广告流程移除；`claimReward.nextAd` 非空时直接展示原弹窗，null 或缺省时停止。后续每条广告仍须完整观看并成功领取，再消费新的 nextAd；取消、路由切换和前后台约束保留。服务端同时返回目标、数量及原 Offer 配置，客户端不猜测解锁状态。

协议见同级服务端 `docs/reward-next-ad-contract-2026-09-21.md`。以下记录仅保留为迭代历史，不再代表当前客户端实现。没有发布或真机效果验收。

## 第二轮：使用现有批量接口并拆分计时

- 正式 API 已提供 `resolvePlayBatch`，提示目标查询改为每组一次批量请求，而不是四次单集 HTTP 请求。保留缺少批量能力的适配器兼容路径；失败不回退重发四次请求。
- 校验批量结果数量、顺序和剧集 ID；结果不匹配时记录脱敏故障并结束连续广告，不猜测目标。
- `episode_ad_return_claim_completed` 记录第一条广告关闭后等待领奖的耗时；`automatic_unlock_claim_completed` 记录连续广告的同阶段耗时；`automatic_unlock_prompt_ready` 记录领取后查询到提示就绪的耗时（不等同于屏幕实际绘制时间）。日志不包含广告凭据。
- 聚焦测试 17 项通过，覆盖批量查询及故障；全项目验证通过。当前实现仍需先确认领奖再确认下一目标，没有声称去掉所有等待，尚未得到新版真机的分段耗时。若领取段占主要耗时，继续调整客户端查询不能解决该段问题。

## 已确认的客户端等待

当前调用链为广告完整结束 → 服务端领奖确认 → 查询后续分集 → 显示连续解锁提示。当前集的重新验权和媒体准备已经并行，不是弹窗的前置条件；后续集原来逐集串行查询，一次解锁多集时会累积多次网络往返。尚无本次真机分段耗时，不能认定全部延迟来自该路径。

## 调整

- 领取确认后最多四集一组并行验权，按目录顺序消费结果；找到首个符合条件的入口就显示提示，不等待更远请求。
- 不从旧目录猜测权益，不提前领取；每次新奖励后清除旧查询结果，重新确认下一目标。
- 取消后不启动新广告或新一批查询；已发出的只读请求仍允许完成，失败有脱敏日志且不产生未处理拒绝。
- 不改两个弹窗的文案、样式及三秒倒计时。

## 验证边界

新增回归先验证串行行为失败，再验证并行顺序、远端慢请求不阻塞当前提示、取消、错误日志脱敏和批量领奖后旧结果失效。聚焦测试 13 项通过。真机需要加载新版后复测；本次没有打包、上传或部署，服务端领奖及首个目标验权的必要等待仍存在。
